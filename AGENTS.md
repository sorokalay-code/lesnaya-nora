# Правила для ИИ-агентов

Эти правила действуют для всего репозитория «Лесная нора». Перед изменением архитектуры ознакомьтесь с [docs/architecture.md](docs/architecture.md), перед изменением сборки и ресурсов — с [docs/deployment.md](docs/deployment.md). Явные указания пользователя имеют приоритет.

## Стек и типизация

- Пишите код и служебные скрипты на TypeScript (`.ts`, `.tsx`). Не возвращайте проект к JS/MJS без конкретной технической необходимости.
- Используйте существующие Node.js и pnpm, версии и зависимости проекта. Не обновляйте глобальные инструменты ради задачи. Изменения зависимостей сопровождайте обновлением `pnpm-lock.yaml`.
- Сохраняйте строгую типизацию игрового кода. Не обходите ошибки через `any`, `@ts-ignore`, `@ts-nocheck` или отключение проверок. Необходимое приведение типа должно иметь проверяемое основание; данные извне сначала проверяйте.
- Используйте предметные интерфейсы, discriminated unions и именованные типы вместо неясных словарей и длинных наборов флагов.

## Декомпозиция и ООП

- У класса, компонента и модуля должна быть понятная ответственность. При добавлении механики выбирайте подходящий предметный модуль или выделяйте новый.
- `Game` координирует сессию и игровой цикл. Не накапливайте в нём правила питания, размножения, инвентаря, диалогов или поведение конкретных животных.
- Для каждого нового вида животного создавайте отдельный класс в `src/game/animals`. Используйте существующую иерархию `Animal`, `Rabbit`, `Predator`, `ForestAnimal` и фабрику `AnimalFactory`.
- Наследование используйте для отношения «является разновидностью», общие алгоритмы держите в базовом классе. Характеристики вида задавайте типизированным профилем. Различия поведения оформляйте методами расширения или стратегиями, а не цепочками проверок вида во всех системах.
- Независимые механики объединяйте композицией. Передавайте зависимости через конструкторы, небольшие типизированные контексты и callbacks; не передавайте весь `Game` ради доступа к нескольким полям.
- Соблюдайте инкапсуляцию. Не обращайтесь к приватным полям через приведения типов и не создавайте неявные глобальные зависимости.
- Применяйте фабрику, шаблонный метод, стратегию, реестр команд и фасад там, где они упрощают расширение. Не создавайте абстракции и глубокие иерархии только ради названия паттерна.
- Устраняйте дублирование предметных правил. Не допускайте нескольких независимых реализаций одной формулы или проверки доступности действия.

## Интерфейс и состояние

- Используйте компоненты из `src/ui/kit` для элементов интерфейса. Если подходящего компонента нет, добавьте его в UI-kit и примените на экране. Общие цвета, размеры и состояния оформляйте через CSS-переменные темы. Игровые правила и состояние экранов держите за пределами UI-kit.
- Интерфейс реализуйте React-компонентами; состояние интерфейса храните в Zustand. Не создавайте параллельный интерфейс через `innerHTML` и ручное управление DOM.
- Правила игры, сохранения и объекты Three.js остаются в движке. Не переносите их в React-компоненты и Zustand.
- Передавайте в UI простые типизированные данные через presenters и `GameUI`; пользовательские действия возвращайте движку через команды.
- Разделяйте компоненты по назначению, подписывайте их только на необходимые данные. Не обновляйте весь React-интерфейс на каждом кадре Three.js.
- При изменении ввода проверяйте фокус полей, ввод текста, закрытие меню, захват указателя и возврат к управлению персонажем.

## Читаемость и форматирование

- Оставляйте пустую строку между методами, конструкторами и аксессорами класса. Не склеивайте конец одного метода с началом следующего.
- Разделяйте пустыми строками логические этапы: проверки условий, подготовку данных, изменение состояния и побочные эффекты. Отделяйте ранний выход от основного алгоритма. Не вставляйте пустую строку после каждой строки подряд.
- Пишите несколько последовательных действий на отдельных строках. Избегайте длинных цепочек операторов, вложенных тернарных выражений и чрезмерно плотных объявлений переменных.
- Используйте понятные названия. Короткие имена вроде `x`, `z`, `dt` допустимы для общепринятых координат и времени; для предметных сущностей выбирайте содержательные имена.
- Выносите значимые игровые коэффициенты в именованные параметры, профили или константы с понятными единицами измерения.
- Упрощайте вложенность ранними выходами и небольшими методами, когда это помогает чтению. Не дробите простой код на бессодержательные обёртки.
- Следуйте `.prettierrc.json`. Форматтер не заменяет ручную проверку читаемости и логического разделения кода.

## Комментарии и документация

- Перед каждым классом пишите короткий JSDoc-комментарий на русском языке: назначение и граница ответственности класса.
- Комментируйте сложные алгоритмы и неочевидные решения: навигацию по раскопам, преобразования координат, коллизии, жизненный цикл семьи, оптимизации и правила кэширования ресурсов.
- Объясняйте причину решения, ограничения и инварианты. Не пересказывайте очевидные действия строка за строкой.
- При изменении поведения обновляйте связанные комментарии. Не оставляйте устаревшие объяснения, закомментированный старый код и TODO без конкретного смысла.
- При изменении архитектуры, управления, скриптов или правил публикации обновляйте соответствующие документы и README.

## Производительность и ресурсы

- Сохраняйте существующие LOD, instancing, отсечение невидимых объектов и ограничение частоты обновлений. Не добавляйте массовые выделения памяти, загрузки ресурсов или поиск по всему миру в кадровый цикл.
- Переиспользуйте геометрию, материалы и загруженные ресурсы. Учитывайте владельца ресурса при освобождении; не уничтожайте общие материалы отдельного экземпляра.
- Новые обработчики событий и подписки должны иметь понятный жизненный цикл и очистку при завершении работы владельца.
- Модели, текстуры и звуки размещайте в `public`; пути в игровом коде получайте через `assetUrl`. Не используйте корневые `/models/...`, `/textures/...` и `/sounds/...`: игра публикуется в подкаталоге GitHub Pages.
- При добавлении вида обновляйте реестры моделей и предусмотрите LOD. После изменения генератора запустите `pnpm run models` и включите необходимые результаты в коммит. Не затирайте вручную подготовленные ресурсы без необходимости.

## Проверки и завершение работы

- Для изменений логики добавляйте или обновляйте тесты наблюдаемого поведения и регрессий. Тестируйте результат, а не копию реализации. Для чисто текстовых правок не создавайте формальные тесты без пользы.
- Для изменений кода перед завершением запускайте `pnpm run check`: форматирование, структуру классов, тесты, типизацию, сборку и проверку ресурсов деплоя.
- При изменении моделей или отрисовки дополнительно используйте подходящий аудит: `pnpm run audit:models`, `pnpm run audit:scene`. Проверяйте интерфейсные изменения в браузере, если он доступен.
- Не исправляйте проверки их отключением и не заявляйте об успешной проверке, если она не запускалась или завершилась ошибкой. Укажите конкретные непроверенные места и причину.
- Избегайте несвязанных изменений. Сохраняйте чужие правки; не сбрасывайте рабочее дерево и не восстанавливайте старую совместимость сохранений без необходимости задачи.
- В итоговом сообщении кратко указывайте, что изменилось, какие проверки выполнены и что осталось сделать пользователю. Сообщения коммитов пишите на русском языке.
- После завершения изменений и успешных проверок всегда создавайте коммит и отправляйте его в удалённый репозиторий. Для деплоя достаточно пуша в `main`; результата GitHub Actions ждать не нужно.
